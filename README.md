## 1. サービス概要
- **どんなサービスか：** Discordの雑談チャットで流れてしまうPCゲーム特有のリンク（VRChatワールドやMod等）と画像（設定画面や座標等）を拾い上げ、グループとして紐づけてストック・検索できる、Discordサーバー連携型の情報整理ツール。
- **誰の、どんな課題を、どう解決するか：** 固定メンバーでPCゲームを遊ぶコミュニティの、「過去に共有されたリンクとそれに関連する画像がバラバラになり、探しにくい」という課題を、Discordのサーバー（Guild）単位でのアクセス制御と、情報の構造的な紐づけ（リレーション）によって解決する。

## 2. このアイデアはどこから生まれたか
### 2-1. きっかけとなった体験・感情
いつもの友人たちとDiscordで通話や雑談をしている際、「今度このゲームをやろう」「このVRChatワールドに行ってみたい」とやりたいことのリンクを貼ったり、遊んだ後に撮ったスクリーンショットや設定画面を共有したりして日々コミュニケーションを取っていました。
しかし数日後、「あの時貼ってくれたリンクどこだっけ？」「あのワールドの画像どれだっけ？」と思った際、日々のチャットはどんどん上に流れていってしまうため、過去のリンクや画像を遡って探すのが非常に難しく、もどかしい経験を多々してきました。

### 2-2. なぜそれが「気になった」のか
私自身、日頃からプログラミングやデータ管理の学習を通して、情報の構造化や作業の効率化に関心を持っているためです。Discord内で共有される有益な情報（マルチプレイ用のMod環境の解説、Web上のリンク、設定画面のキャプチャなど）が、リアルタイムの雑談のログに埋もれ、二度と再利用しにくくなる状態に対して強い非効率さを感じていました。
情報を「フロー（流れるもの）」のまま終わらせず、適切に「ストック（蓄積・検索できるもの）」として整理・紐づけを行うことで、次回プレイ時の準備やトラブルシューティングの手間を大幅に削減できると考え、この課題の解決に関心を持ちました。

## 3. 課題の整理（表面的になっていないか）
### 3-1. 表に見えている困りごと
Discordの雑談チャットや標準機能だけでは、過去に共有した「リンク（Modやワールド）」や「画像（設定や思い出）」の検索性が低く、それぞれの情報が紐づいていないため探しにくい。

### 3-2. 本当に解決したい課題は何か
- **なぜ？：** 過去の写真やリンクを探しにくいとなぜ困るのか？
  → 「このVRChatワールドのURL」と「そこで撮った写真」や、「このModのリンク」と「その設定画面のスクショ」など、セットで確認したい情報がバラバラになってしまうから。
- **なぜ？：** 情報がバラバラだとどう困るのか？
  → 遊び始める前の準備（環境構築やワールド探し）に時間がかかり、スムーズにマルチプレイを開始できないから。
- **なぜ？：** スムーズに開始できないとなぜ困るのか？
  → 限られた時間で集まっているのに、無駄な確認作業によってゲームそのものを楽しむ時間が損なわれてしまうから。
- **本当に解決したい課題：**
  「Discordの仕様上、点と点で散らばってしまう情報を線（意味のある塊）として整理し、いつでも瞬時に引き出せるようにすること」

## 4. 想定ユーザーについて
### 4-1. 想定しているユーザー
- **年齢：** 20代
- **理由：** 学生時代に比べて集まれる時間が限られてきており、限られた時間の中で効率的に集まって遊びたいと考える年代だから。
- **生活・状況：** 週末や夜に、Discordでいつもの友人グループ（5人程度）と通話しながら、サバイバルゲームやVRChatを遊んでいる。
- **理由：** 協力してひとつのワールドを開拓したり、色々なワールドを巡ったりする遊び方は「Modの導入手順」や「座標データ」など共有する情報の質が複雑になりやすいため。
- **環境：** Discordを日常のコミュニケーションインフラとしており、PCゲームをメインに遊んでいる。
- **理由：** Webブラウザを開きながらゲームをする環境があり、OAuthログインなどのWebの仕組みに抵抗がないため。

### 4-2. 自分とユーザーの距離
**自分自身（および自分の友人グループ）**
理由：自分自身が最初のユーザーになることで、情報の整理における検索性や、画面の使い勝手の解像度を最も高く保つことができるため。

### 4-3. 実際に使われる可能性について(需要・存在確認)
- **まず最初に使ってくれそうな人は誰か？：** いつも一緒にゲームをしている友人たち。
- **どんな場面で思い出すか？：** 以前共有したModの導入URLや、過去に行ったVRChatワールドのURL、ゲーム内の座標メモなどを再確認したい時。
- **代わりに使っているものは何か？：** Discordのフォーラム機能、専用チャンネル分け＋ピン留め運用、Notion、Raindrop.ioなどのブックマーク管理ツール。
- **置き換えてまで使う理由：** 既存コミュニティの「雑談ベースのコミュニケーションフロー」を一切邪魔することなく、かつ個々のリンク・画像を意味のある単位で紐づけて管理できる専用ツールが必要なため。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)
- **きっかけ：** コミュニティの管理者が本アプリ（Discordアプリ）をサーバーに導入する。
- **最初の一歩：** ユーザーはDiscord上で保存したいメッセージを右クリックし、「アプリ」＞「この情報を保存」を押すだけ。初回未ログイン時はBotから専用のログインURL（Ephemeral Message）が通知され、Webで認証後に再度コマンドを実行することでシームレスに保存できる。
- **継続の理由：** わざわざブラウザを開くことなく、雑談の流れの中で直感的に保存・紐づけが完了する。「今すぐ思い出したい」場面ではDiscord内のスラッシュコマンドで即座に検索でき、「じっくり見返したい・整理したい」場面ではWebアプリで詳細に確認できるという使い分けができる実用性を実感できるため。

## 5. 既存サービス・競合調査
### 5-1. 似たサービスの調査
- **Notion：** 柔軟なデータベース作成と情報管理が可能なドキュメントツール。
- **Raindrop.io / Pocket：** URLをタグ付けして保存できる強力なブックマーク管理アプリ。
- **Discord（フォーラム機能）：** チャンネル内でスレッドを立て、最大20個のタグ付けとフィルタ検索が可能な標準機能。
- **Discord（専用チャンネル分け＋ピン留め運用）：** ゲームやトピックごとにチャンネルを分け、重要なメッセージをピン留めして管理する運用方法。ピン留めの上限は2025年のアップデートで50件から250件に緩和されている。

### 5-2. それでも自分が作りたい理由
既存ツールはいずれも一長一短という状態です。
Raindrop.ioなどのブックマークツールは「URLと複数枚の画像・補足テキストを1つの塊としてリレーショナルに管理する」というゲーマー特有の用途に適していません。Notionは高機能ですが、雑談中にわざわざ別アプリを開いて入力する手間が重すぎます。
また、Discordのフォーラム機能はタグ検索が可能ですが、「新しいスレッドを立てる」という事前の運用ルールを強いることになります。

「専用チャンネル分け＋ピン留め」という運用による代替も検討しましたが、2つの限界があると考えています。1つ目は、フォーラム機能と同様に「これは専用チャンネルに貼るべき情報だ」という判断をメンバー全員が常に強いられる点です。雑談の流れの中で自然に貼られるリンクや画像を、その都度正しいチャンネルへ振り分ける運用は、結局「運用ルールを強いない」という思想と矛盾します。2つ目は、ピン留めやチャンネル分けが「トピック単位」の整理にとどまり、「このURLとこの画像はセットだった」という**アイテム単位の関連付け**を表現できない点です。ピン留めは個々のメッセージを固定するだけで、メッセージ同士の関係性を構造化する手段ではありません。

**「普段の雑談チャンネルに流れたリンクや画像を、既存のコミュニケーションを邪魔せずに後から拾い上げ、アイテム単位で意味のある塊として紐づける」**というアプローチをとるツールが存在しない点に課題を感じました。

### 5-3. 差別化を「体験価値」で表現する
- **私のアプリの差別化ポイント：**
  「ブラウザを開く手間すら不要。Discordのチャット上の右クリック（長押し）だけで情報を瞬時にキャプチャし、『今すぐ思い出したい』時はDiscord内のスラッシュコマンドで即座に検索、『じっくり見比べたい・整理したい』時は専用Web画面で扱える、用途に応じて使い分けられるコミュニティ専用拡張辞書体験」

## 6. このサービスで提供したい価値
### 6-1. ユーザーの変化
- **行動の変化：** 情報が共有された瞬間に、Discord上でそのままメニューを開きワンクリックで保存する習慣ができる。「後から思い出しながらブラウザで整理する」という心理的ハードルの高い作業が消滅する。
- **気持ちの変化：** 「あの情報どこだっけ」と探すストレスがなくなり、スムーズに目的のゲームやワールドを遊び始めることができる。
- **考え方の変化：** 日々の雑談で共有される情報が、一時的なものではなく、コミュニティ内でいつでも再利用可能な「共有のデータベース」であると感じられるようになる。

### 6-2. 価値を一文で表す
「このサービスは、PCゲームを遊ぶコミュニティが、Discordの雑談を邪魔せずワンクリックで流れる情報をキャプチャ・紐づけ整理し、Discord内での即時検索とWebでのじっくりした整理・管理を使い分けながら、いつでも瞬時に引き出せるようになるサービス。」

### 6-3. 定量的な成功指標（仮説）
導入前はDiscordの過去ログ検索やメンバーへの確認作業（実測値）で平均3〜5分かかっていた情報へのアクセス時間を、本アプリのタグ検索とグループ化により**「10秒以内」**に短縮することを目指す。本番導入後、友人グループでの実際のゲーム準備において、目的の情報到達までの時間をストップウォッチで計測し効果を検証する。

## 7. このアプリで実現すること
### MVPで作る機能
**① Discord連携機能（情報のキャプチャ・サジェスト・即時検索）**
- **メッセージコマンドによる即時保存：** Discordのメッセージ右クリック（スマホは長押し）メニューから「この情報を保存」を選択するだけで完了するキャプチャ機能。DiscordのHTTP Interactionsエンドポイントを利用し、常時接続不要なステートレス構成で実装する。
- **サジェスト応答と3秒ルール対応：** コマンドを受信すると即座に「処理中（Deferred Response）」を返し、実際の保存処理はSolid Queueを用いた非同期ジョブで実行する。処理完了後、Discord上に「直前の投稿と紐づけますか？」というボタン付きメッセージを返し、Discord内で紐づけ操作を完結させる。
- **検索スラッシュコマンド：** `/search VRChat`のように、Discord上でタグ・キーワードによる検索が完結する機能。「素早く1件を思い出したい」という日常的なニーズは、ブラウザを開かずここで完結させる。

**② Webアプリ機能（閲覧・整理・管理）**
- **認証・アクセス制御基盤：** Discord OAuthログイン機能。Guild ID（サーバーID）に基づき、同じサーバーのメンバーしか閲覧できない安全な認可設計。
- **横断的な閲覧・整理機能：** タグ別・時系列でのグリッド表示など、大量の情報を横断的に見比べられるビューを提供する。サジェストで紐づけそびれた「未整理」の情報は、この画面から手動で既存のグループに紐づけ（整理）できる。
- **管理機能：** 投稿の編集・削除（作成者本人のみ）、タグの編集など、Discordのチャットインターフェースでは完結しない管理系の操作を担う。

### 本リリースで作る機能
- リンクのOGPプレビュー情報の取得・表示機能（Solid Queueを利用したバックグラウンド非同期処理）。
- ドメイン（URL）に基づく、タグの自動付与機能。

## 8. このアプリの懸念点とその対策
### 8-1. 外部API連携時のUXとパフォーマンス制約
- **何が問題になりそうか：** DiscordのInteractions APIは「リクエスト受信から3秒以内に応答（ACK）を返さないと無効になる」という厳格な制約がある。画像を含むメッセージの処理や外部API連携を同期的に行うと、この3秒ルールを超過してエラーになる懸念がある。
- **そのために考えている対策：** Webhookを受信したRailsのエンドポイントでは、検証のみ行い即座に「Deferred Response」をDiscordに返す。重い保存処理はRails 8標準のSolid Queueにジョブとして渡し、非同期処理が完了次第、フォローアップWebhookを利用して結果をユーザーに通知するアーキテクチャとする。

### 8-2. APIエンドポイントのセキュリティ担保
- **何が問題になりそうか：** インターネット上に公開されたDiscord向けのエンドポイントに対して、悪意のある第三者から偽装リクエストが送信されるリスク。Discordからの正規リクエスト以外を弾かないと、不正なデータがDBに書き込まれてしまう。
- **そのために考えている対策：** Discordの仕様に従い、ヘッダーに付与される `x-signature-ed25519` を利用した公開鍵暗号による署名検証を実装する。検証に失敗したリクエストは即座に `401 Unauthorized` を返すセキュアな設計を徹底する。

### 8-3. Discord内検索とWebアプリの役割の重複
- **何が問題になりそうか：** 検索機能をDiscordのスラッシュコマンドとWebアプリの両方に持たせると、ユーザーがどちらを使えばよいか迷い、Webアプリの存在意義が薄れてしまう懸念がある。
- **そのために考えている対策：** 「素早く1件を思い出す」用途はDiscordのスラッシュコマンド、「大量の情報を横断的に見比べる・整理する・管理する」用途はWebアプリ、という役割分担を明確にし、Webアプリ側は単純なキーワード検索よりも、タグ別グリッド表示や手動整理といった、チャットインターフェースでは実現しにくい機能に重点を置く。

## 10. 技術スタック（手段としての技術）
### 10-1. 使用予定の技術
- **フレームワーク：** Ruby on Rails 8
- **DB：** PostgreSQL
- **デプロイ先：** Render (Web, PostgreSQL) / Cloudinary または Amazon S3 (画像保存)
- **使用予定ライブラリ：** OmniAuth (ログイン用), Ransack (検索用), Solid Queue (非同期処理), `ed25519` / `rbnacl` (署名検証用)

### 10-2. 技術選定の比較検討
| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails 8 | 採用 | DBの構築とWebのUI作成を最速で行いつつ、DiscordのHTTP Interactionsを受信するAPIエンドポイントと、Solid Queueによる非同期ジョブを単一のインフラ（Renderの無料枠）で統合・実装するため。 |
| React/Next.js | 不採用(現時点) | MVPのコア体験が「Discord上でのメッセージコマンド・スラッシュコマンド」にシフトしたため、フロントエンドのリッチ化よりバックエンドとAPI連携の開発にリソースを集中させるべきと判断。 |

- **今回チャレンジしたい点：**
  - Discordのメッセージコマンド・スラッシュコマンド（Application Commands）をHTTP Interactionsエンドポイントで受信し、署名検証（Ed25519）、Deferred Response、Solid Queueとの連携までを含めた一連の実装。
  - DiscordのGuild IDを用いた安全なマルチテナント（アクセス制御）設計。
  - 親要素と子要素、およびタグによる多対多の複雑なデータベース設計。

### 10-3. キャッチアップ不足の懸念
**1. Discord Interactionsの署名検証とセキュリティ実装**
リクエストが本当にDiscordから送信されたものかを検証する `Ed25519` 署名検証の実装は未経験の領域です。検証ロジックをRailsのミドルウェアやコントローラに正しく組み込むための調査・キャッチアップに一定の時間を要する可能性があります。

**2. Application Commandsの登録とライフサイクル管理**
Discordのコマンド登録は、グローバル登録では反映に遅延が生じるため、開発効率を上げるには特定のサーバー向けに登録する（Guild-scoped）設計が推奨されます。このAPIを通じたコマンドの登録・更新・削除スクリプトをRailsタスク等で構築する運用ノウハウがなく、仕様把握に時間がかかる懸念があります。

**3. Solid Queueを用いた非同期処理の設計**
3秒ルールを回避するための「非同期ジョブ化」において、Rails 8から標準導入されたSolid Queueの環境構築を行う必要があります。本番環境でのジョブのリトライ制御や、処理完了後にDiscordへ結果を返す（Follow-up Message）非同期特有のフローにおいて、見積もり以上の時間がかかる可能性があります。
