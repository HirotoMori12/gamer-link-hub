## 1. サービス概要
- **どんなサービスか：** Discordの雑談チャットで流れてしまうPCゲーム特有のリンク（VRChatワールドやMod等）と画像（設定画面や座標等）を拾い上げ、グループとして紐づけてストック・検索できる、Discordサーバー連携型の情報整理ツール。
- **誰の、どんな課題を、どう解決するか：** 固定メンバーでPCゲームを遊ぶコミュニティの、「過去に共有されたリンクとそれに関連する画像がバラバラになり、探しにくい」という課題を、Discordのサーバー（Guild）単位でのアクセス制御と、情報の構造的な紐づけ（リレーション）によって解決する。

---

## 2. このアイデアはどこから生まれたか
### 2-1. きっかけとなった体験・感情
いつもの友人たちとDiscordで通話や雑談をしている際、「今度このゲームをやろう」「このVRChatワールドに行ってみたい」とやりたいことのリンクを貼ったり、遊んだ後に撮ったスクリーンショットや設定画面を共有したりして日々コミュニケーションを取っていました。
しかし数日後、「あの時貼ってくれたリンクどこだっけ？」「あのワールドの画像どれだっけ？」と思った際、日々のチャットはどんどん上に流れていってしまうため、過去のリンクや画像を遡って探すのが非常に難しく、もどかしい経験を多々してきました。

### 2-2. なぜそれが「気になった」のか
私自身、日頃からプログラミングやデータ管理の学習を通して、情報の構造化や作業の効率化に関心を持っているためです。Discord内で共有される有益な情報（マルチプレイ用のMod環境の解説、Web上のリンク、設定画面のキャプチャなど）が、リアルタイムの雑談のログに埋もれ、二度と再利用しにくくなる状態に対して強い非効率さを感じていました。
情報を「フロー（流れるもの）」のまま終わらせず、適切に「ストック（蓄積・検索できるもの）」として整理・紐づけを行うことで、次回プレイ時の準備やトラブルシューティングの手間を大幅に削減できると考え、この課題の解決に関心を持ちました。

## 3. 課題の整理（表面的になっていないか）
### 3-1. 表に見えている困りごと
Discordの雑談チャットや標準機能だけでは、過去に共有した「リンク（Modやワールド）」や「画像（設定や思い出）」の検索性が低く、それぞれの情報が紐づいていないため探しにくい。

### 3-2. 本当に解決したい課題は何か
- **なぜ？：** 過去の写真やリンクを探しにくいとなぜ困るのか？
  → 「このVRChatワールドのURL」と「そこで撮った写真」や、「このModのリンク」と「その設定画面のスクショ」など、セットで確認したい情報がバラバラになってしまうから。
- **なぜ？：** 情報がバラバラだとどう困るのか？
  → 遊び始める前の準備（環境構築やワールド探し）に時間がかかり、スムーズにマルチプレイを開始できないから。
- **なぜ？：** スムーズに開始できないとなぜ困るのか？
  → 限られた時間で集まっているのに、無駄な確認作業によってゲームそのものを楽しむ時間が損なわれてしまうから。
- **本当に解決したい課題：**
  「Discordの仕様上、点と点で散らばってしまう情報を線（意味のある塊）として整理し、いつでも瞬時に引き出せるようにすること」

## 4. 想定ユーザーについて
### 4-1. 想定しているユーザー
- **年齢：** 20代
- **理由：** 学生時代に比べて集まれる時間が限られてきており、限られた時間の中で効率的に集まって遊びたいと考える年代だから。
- **生活・状況：** 週末や夜に、Discordでいつもの友人グループ（5人程度）と通話しながら、サバイバルゲームやVRChatを遊んでいる。
- **理由：** 協力してひとつのワールドを開拓したり、色々なワールドを巡ったりする遊び方は「Modの導入手順」や「座標データ」など共有する情報の質が複雑になりやすいため。
- **環境：** Discordを日常のコミュニケーションインフラとしており、PCゲームをメインに遊んでいる。
- **理由：** Webブラウザを開きながらゲームをする環境があり、OAuthログインなどのWebの仕組みに抵抗がないため。

### 4-2. 自分とユーザーの距離
**自分自身（および自分の友人グループ）**
理由：自分自身が最初のユーザーになることで、情報の整理における検索性や、画面の使い勝手の解像度を最も高く保つことができるため。

### 4-3. 実際に使われる可能性について(需要・存在確認)
- **まず最初に使ってくれそうな人は誰か？：** いつも一緒にゲームをしている友人たち。
- **どんな場面で思い出すか？：** 以前共有したModの導入URLや、過去に行ったVRChatワールドのURL、ゲーム内の座標メモなどを再確認したい時。
- **代わりに使っているものは何か？：** Discordのフォーラム機能、Notion、Raindrop.ioなどのブックマーク管理ツール。
- **置き換えてまで使う理由：** 既存コミュニティの「雑談ベースのコミュニケーションフロー」を変えることなく、後から情報を構造化してストックできる専用ツールが必要なため。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)
- **きっかけ：** コミュニティの管理者が本アプリを導入し、Discordチャンネルに招待リンクを貼る。
- **最初の一歩：** ユーザーは「Discordアカウントでログイン」をクリック。アプリ側で所属しているDiscordサーバー（Guild ID）を取得し、サーバーごとの専用ワークスペースに自動で振り分けられる。
- **継続の理由：** 共有された情報がタグによって適切に分類・紐づけされ、複数サーバーを掛け持ちしていても各コミュニティの文脈に沿った情報を瞬時に引き出せる実用性を実感できるため。

## 5. 既存サービス・競合調査
### 5-1. 似たサービスの調査
- **Notion：** 柔軟なデータベース作成と情報管理が可能なドキュメントツール。
- **Raindrop.io / Pocket：** URLをタグ付けして保存できる強力なブックマーク管理アプリ。
- **Discord（フォーラム機能）：** チャンネル内でスレッドを立て、最大20個のタグ付けとフィルタ検索が可能な標準機能。

### 5-2. それでも自分が作りたい理由
既存ツールはいずれも一長一短という状態です。
Raindrop.ioなどのブックマークツールは「URLの保存」には優れていますが、「URLと複数枚の画像・補足テキストを1つの塊としてリレーショナルに管理する」というゲーマー特有の用途には適していません。Notionは高機能ですが、雑談中にわざわざ別アプリでDBを構築する手間が重すぎます。
また、Discordのフォーラム機能はタグ検索が可能ですが、「新しいスレッドを立てる」という事前の運用ルールを強いることになります。**「普段の雑談チャンネルに流れたリンクや画像を、既存のコミュニケーションを邪魔せずに後から拾い上げて紐づける」**というアプローチをとるツールが存在しない点に課題を感じました。

### 5-3. 差別化を「体験価値」で表現する
- **私のアプリの差別化ポイント：**
  「既存の雑談フローを変えることなく、流れてしまったリンクや画像を『グループ化（紐づけ）』してストックし、所属するDiscordサーバーごとにアクセス制御された安全な環境で瞬時に引き出せる、コミュニティ専用の拡張辞書体験」

## 6. このサービスで提供したい価値
### 6-1. ユーザーの変化
- **行動の変化：** 後から見返したい情報が共有された際、Discordのチャット内に埋もれさせず、ツールに登録して整理する習慣ができる。
- **気持ちの変化：** 「あの情報どこだっけ」と探すストレスがなくなり、スムーズに目的のゲームやワールドを遊び始めることができる。
- **考え方の変化：** 日々の雑談で共有される情報が、一時的なものではなく、コミュニティ内でいつでも再利用可能な「共有のデータベース」であると感じられるようになる。

### 6-2. 価値を一文で表す
「このサービスは、PCゲームを遊ぶコミュニティが、Discordで流れてしまう過去のリンクや画像を『塊』として紐づけ整理し、いつでも瞬時に検索して引き出せるようになるサービス。」

### 6-3. 定量的な成功指標（仮説）
導入前はDiscordの過去ログ検索やメンバーへの確認作業（実測値）で平均3〜5分かかっていた情報へのアクセス時間を、本アプリのタグ検索とグループ化により**「10秒以内」**に短縮することを目指す。本番導入後、友人グループでの実際のゲーム準備において、目的の情報到達までの時間をストップウォッチで計測し効果を検証する。

## 7. このアプリで実現すること
### MVPで作る機能
- **認証・アクセス制御基盤：** Discord OAuth連携および、DiscordのGuild ID（サーバーID）に基づいたデータアクセス制御機能（同じサーバーのメンバーしか情報を閲覧できない仕組み）。また、誤操作を防ぐため「投稿の編集・削除は作成者本人のみ可能」とする認可設計。
- **情報の紐づけ（リレーション）機能：** 1つの「投稿」に対して、複数の「画像」や「補足テキスト」を子要素としてグループ化して保存できる機能（1対多）。
- **情報の管理：** 投稿・編集・削除機能（CRUD）。
- **タグ付け・検索機能：** 投稿に対する「タグ」の紐づけ（多対多）、およびタグやキーワードによる絞り込み機能。

### 本リリースで作る機能
- リンクのOGPプレビュー情報の取得・表示機能（Solid Queueを利用したバックグラウンド非同期処理）。
- DiscordのWebhookを利用した、アプリからの更新通知機能。

## 8. このアプリの懸念点とその対策
### 8-1. 運用上のハードル（入力の手間）
- **何が問題になりそうか：** ユーザーがわざわざブラウザを開いて情報を登録する手間を面倒に感じ、利用されなくなる懸念。
- **そのために考えている対策：** アプリのUIで画像のドラッグ＆ドロップ対応を実装し操作コストを下げる。将来的にはDiscord Botを作成し、「Discord上で特定の絵文字リアクションをつけるだけで自動ストックされる機能」の開発を視野に入れる。

### 8-2. 技術上のハードル（外部APIと非同期処理）
- **何が問題になりそうか：** 本リリースで予定しているOGP取得において、同期処理で行うとレスポンスが極端に遅くなる、またはスクレイピング先の規約やレート制限に引っかかるリスクがある。
- **そのために考えている対策：** Rails 8標準のSolid Queueを利用して非同期でOGPを取得する設計にする。また、取得失敗時のリトライ処理やタイムアウト設定を適切に組み込み、システム全体が停止しないよう考慮する。

### 今考えている発展案

## 10. 技術スタック（手段としての技術）
### 10-1. 使用予定の技術
- **フレームワーク：** Ruby on Rails 8
- **DB：** PostgreSQL
- **デプロイ先：** Render (Web, PostgreSQL) / Amazon S3 または Cloudinary (画像保存)
- **使用予定ライブラリ：** OmniAuth (Discordログイン用), Ransack (検索機能用), Solid Queue (非同期処理・本リリース時予定)

### 10-2. 技術選定の比較検討
| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails 8 | 採用 | カリキュラムで培った知識を活かしつつ、Solid Queue等の最新機能を活用してインフラをシンプルにし、マルチテナント設計を含むDB設計を期間内に実装するため。 |
| React | 不採用(現時点) | フロントエンドとバックエンドを分離すると初期開発の工数が跳ね上がるため。本リリース以降に必要に応じて検討。 |
| Next.js | 不採用 | OGPの動的生成等に強みはあるが、今回は認証必須のクローズドアプリでありSEOを考慮する必要がないため、RailsのViewで十分と判断。 |

- **今回チャレンジしたい点：**
  1. DiscordのGuild IDを用いた安全なマルチテナント（アクセス制御）設計。
  2. 親要素（投稿）に対して複数の子要素（画像）を持たせる1対多、およびタグ機能による多対多の正確なデータベース設計。
  3. （本リリース以降）Rails 8標準のSolid Queueを用いたOGP取得の非同期処理とエラーハンドリング。

### 10-3. キャッチアップ不足の懸念
**1. Discord OAuth連携とAPIの仕様理解**
外部APIを用いた認証の実装経験が浅いため、DiscordのAPI仕様（Guild IDの取得など）の正確な理解に時間を要する可能性があります。特に、セキュリティを考慮した認可設計（同じサーバーのメンバーしか情報を閲覧できない仕組み）の実装や、そのテスト・検証において、想定以上の工数がかかる懸念があります。

**2. Solid Queueを用いた非同期処理の設計と運用**
本リリース時の非同期処理（OGP取得）に向けて、Rails 8から標準導入されたSolid Queueの環境構築を行う必要があります。従来のSidekiq等とは異なりRedisは不要になりますが、本番環境でのジョブの失敗時のリトライ制御やエラー調査など、非同期処理特有の運用において見積もり以上の時間がかかる可能性があります。
